# Cloud sandbox facts

From the setup probe on 2026-10-12 (Default Cloud Environment). The first probe that day stalled
before timing the build; this entry is from a second probe the same day that ran the build and
test steps to completion (or to their actual failure) and fills in the "TBD" rows below.

| | |
|---|---|
| Machine | Ubuntu 24.04.5 LTS, kernel 6.18.44-fc-v114, 4 cores (Xeon 2.8 GHz), 15 GB RAM, 0 swap. No GPU; Mesa software rasterizers only (`swrast`), no `/dev/dri`, no Vulkan ICD — expect no wgpu adapter |
| **Disk — the real constraint** | `df` reports `/dev/vda` as 252G, but that's not the budget: this session's actual writable allowance is **~40 GB total** (9.1G used + 30G avail at the start ≈ the real ceiling). Once total usage hits ~39 GB, every write fails with ENOSPC — including the harness's own tiny output-capture files, which breaks every shell command (even `df`, `true`) until space is freed. **The only thing that still works at 0 free is deleting files** (`rm -f`/`rm -rf`); that recovers the shell immediately. Plan disk usage around ~40 GB, not the 252G `df` shows |
| Rust | 1.97.0 preinstalled via rustup (stable), clippy + rustfmt already present. Workspace pins only a floor (`rust-version = "1.95"`, no `rust-toolchain.toml`), so nothing needed upgrading. `rustup target add wasm32-unknown-unknown`: 4.2s |
| crates | `cargo fetch`: 13.4s for the whole workspace. Bare `curl` to crates.io/static.crates.io gets 403 (their CDN rejecting a generic request) but cargo's real sparse-index + download traffic is unaffected |
| System packages | None missing. `apps/photocraft` (wgpu/winit/accesskit/atspi) built cleanly with whatever `pkg-config`, `libx11-dev`, `libxkbcommon0`, wayland client/cursor/egl, `libssl-dev` and `libasound2` the base image already has. No `apt-get install` needed |
| GitHub, our fork | `git push` works, including a fast-forward of `main` (18 commits, `538c502..3794ad4`, accepted, no force). Pushing a branch with **no `claude/` prefix is accepted** (this `nightly-notes` branch itself proves it, across two different sessions' pushes to it). `gh auth status` reports a false "token invalid" failure; ignore it — `gh api` calls against the fork work fine (confirmed `admin`/`maintain`/`push` all true) |
| GitHub, other repos | Repos not attached to *this* session hit a hard 403 on the GitHub REST API and on `codeload.github.com` tarballs ("GitHub access to this repository is not enabled for this session"). **Plain `git clone`/`fetch`/`ls-remote` over `https://github.com/...` is not gated this way** — it works for any public repo regardless of session attachment (verified against `storytold/photocraft`, `psd-tools/psd-tools`, `satoshoe-dev/affinity-samples`). The "upstream attached to the nightly routine" note from the first probe did not carry over to this session — `gh api repos/storytold/photocraft` still 403'd here, so repo attachment looks like a per-session setting, not a durable one. Don't rely on it persisting; use plain `git` for upstream reads regardless |
| Corpus | `cargo xtask corpus --all` **cannot complete unattended in a session like this one**: `PngSuite` (`www.schaik.com`, not GitHub) succeeds (176 files, 728 KB), but the very next corpus (`psd-tools`, fetched via `codeload.github.com` per `xtask/src/pinned.rs`) 403s for the same repo-scope reason as above, and every other pinned corpus is fetched the same codeload way, so they'd all fail too. Fix requires either (a) a durable repo allowlist covering the ~11 external pinned repos for whatever session runs the nightly job, or (b) changing `xtask/src/pinned.rs` to fetch via plain `git clone`/`git archive` instead of `codeload.github.com`, since plain git to those same repos is not gated. Until one of those lands, skip `cargo xtask test-corpus` and the `corpus` feature in nightly runs — treat them as not runnable here |
| `cargo test --workspace --no-run` | **Failed — ran out of the ~40 GB disk allowance before finishing.** Right after the release build (`target/` at 1.9 GB), this ballooned `target/debug` to ~37+ GB and crashed with ENOSPC, taking the shell down with it (see the Disk row). Recovered with `rm -rf target/debug` (reclaimed ~27 GB). **Do not run a workspace-wide `cargo test`/`cargo clippy --workspace --all-targets` in one shot here** — budget per-crate or per-area runs instead, with `rm -rf target/debug` (or `cargo clean -p <crate>`) between unrelated batches |
| Waiting | The first probe warned "never start a long build in the background and end the turn to wait: nothing wakes an unattended run." That did **not** hold in this session: backgrounding `cargo build --release` and `cargo test --workspace --no-run` and ending the turn both produced a completion/failure notification that resumed the run normally. Still run with a generous timeout either way, foreground or background, since environments may differ |
